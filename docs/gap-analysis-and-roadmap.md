## 1. 参考项目的真实情况（已读源码，修正 v1 结论）

代码 5033 行，20 个模块，5 步流水线（`run.py`）：采集 → 六维打分 → 回测 → 组合优化 → 单文件仪表盘。

**它没有用 akshare。** `requirements.txt` 原文：「原《新手上手指南》里写的 akshare / quantstats 代码里并未 import，无需安装」。实际数据源是：

| 用途 | 接口 |
|---|---|
| 实时快照（价格/涨跌/换手/量比/PE/PB/市值） | `qt.gtimg.cn`（腾讯，GBK） |
| 历史日线（**前复权**） | `web.ifzq.gtimg.cn/appstock/app/fqkline/get`，单次上限 640 根，需分段 |
| 个股估值 + 全 A 横截面估值 | 东财 `RPT_VALUEANALYSIS_DET` |
| 财务指标 | 东财 `RPT_LICO_FN_CPD` |

**可复用的真实资产（这次是源码，可以直接抄）：**

| 模块 | 可复用内容 | 复用方式 |
|---|---|---|
| `analyst_brain.py` | 六维指标清单、`_s/_rs` 线性映射、`score_trend/momentum/volume/risk/valuation/quality` 的**具体公式与阈值**、`trade_signal` 动作规则、滚动分位 `rolling(250).rank(pct=True)` | 公式直接搬，**循环必须向量化** |
| `backtest_engine.py` | 大盘三档择时、T+1 开盘成交、一字涨跌停/停牌过滤、顺延卖出、板块 10%/20% 阈值、费用口径、IS/OOS 滚动 70/30、参数网格、`_stats_from_returns` 指标口径 | 规则全部保留，**引擎重写**（见 §6） |
| `portfolio_opt.py` | Ledoit-Wolf 协方差 + HRP 配权 + 最小波动/最大夏普 | 直接复用 |
| `config.py` | 权重、评级阈值、费用、IS 比例等默认值 | 抄默认值，但改为 YAML 可配 |
| `collect_data.py` | 东财两个报表接口的字段清单与分页/过滤坑（必须按 `TRADE_DATE` 过滤，否则横截面失真） | 接口清单直接抄 |

**必须改掉的：**

1. **逐行 Python 循环打分**：`analyst_brain` 对每只股票逐行调用 4 个打分函数。24 只 × 1500 行尚可，300 只 × 4400 行会到千万级函数调用，实测会从秒级退化到几十分钟。→ 全部向量化。
2. **股票池硬编码 24 只**：`config.POOL`。→ 改为 universe 表驱动。
3. **前复权价格进回测**：见 §3。→ 换后复权。
4. **分数是绝对刻度（0~100 线性映射）**：全市场普涨时所有股票分数都高，无法区分。→ 综合分改为**横截面百分位**，绝对分保留作展示。
5. **估值/质量维无历史时点**：`REPORTDATE` 是报告期末，不是公告日，直接用于历史会提前 1~3 个月用上未公布财报。→ 必须补公告日，否则这两维只能用于当日推荐。

## 2. 数据库：需要吗？

**结论：不需要数据库服务器，但需要「列式文件仓 + 嵌入式查询引擎」。**

先把量算清楚：

| 场景 | 行数 | Parquet 体积 | 说明 |
|---|---|---|---|
| HS300 × 18 年 | 300 × ~4400 ≈ **132 万行** | 25~40 MB | 比一张手机照片还小 |
| 主板全量 × 18 年 | ~3200 × 4400 ≈ **1400 万行** | 300~500 MB | 单机内存可整表载入 |
| 每日打分快照 | 300~3200 行/天，7.5~80 万行/年 | < 50 MB/年 | 用于回溯与版本对比 |

这个量级下，MySQL/PostgreSQL/ClickHouse 都是过度设计：

- 你的访问模式是「**每天收盘后整表批量读 → 向量化计算 → 写回快照**」，不是高并发点查；
- 单机、单用户、无并发写入；
- 装一个数据库服务器，换来的是运维成本、备份策略、连接池、迁移脚本，而不是性能。

**推荐组合（零部署）：**

```
Parquet（按年分区）+ DuckDB（进程内 SQL）+ SQLite（只存任务状态/元数据）
```

- **Parquet**：`data/bars/year=2024/part.parquet`，列式压缩、按列裁剪，读 300 只的收盘价只花几十毫秒；
- **DuckDB**：`duckdb.sql("select ... from 'data/bars/*.parquet'")`，可直接对 Parquet 做 SQL + 窗口函数，也能 `df.to_parquet` 互转，无需服务进程；
- **SQLite**：只存 `job_runs`（任务执行记录）、`score_versions`（版本元数据）这类几十行的小表。

**真正需要设计的不是选型，而是三件事：**

1. **分区键**：`year` + 可选 `board`，保证按年增量写入、按年回溯；
2. **快照版本**：打分结果必须带 `score_version` + `as_of_date` + `data_snapshot`，否则「昨天的分」永远算不回来；
3. **主数据表**：`universe`（代码/名称/板块/行业/上市日/退市日/状态）必须是唯一真相源，行情表只存代码。

**什么时候才需要上 PostgreSQL**：多用户 Web 并发、分钟级/tick 数据、实时写入、需要事务。你现在都不沾。

## 3. baostock vs akshare，以及复权到底怎么算

### 3.1 两者不是同类东西

| 维度 | baostock | akshare |
|---|---|---|
| 本质 | 官方 SDK，固定接口协议 | 爬虫集合，封装东财/新浪/腾讯/同花顺网页接口 |
| 行情 | 日/周/月/5~60 分钟 K 线，`adjustflag` 三口径 | 多源，可指定 `qfq`/`hfq`/不复权 |
| **复权因子** | **提供** `query_adjust_factor`（`foreAdjustFactor` / `backAdjustFactor` 累计因子） | **不提供**，只给复权后的价格 |
| 财务 | 季频三大报表，字段稳定、英文 | 更全（业绩预告/快报/股东户数/分红），字段中文、口径杂 |
| 估值 | **无** PE/PB/PS | 有，东财全 A 横截面（实测 5573 只） |
| 行业 | 证监会行业（较旧） | 东财行业（实测 `BOARD_NAME`：半导体/银行Ⅱ/保险Ⅱ…）、申万、中信 |
| 交易日历 | 有 `query_trade_dates` | 有 |
| 稳定性 | 高，但慢、全局单连接必须串行 | 中低，上游改版即挂，需锁版本 + 重试 |
| 速度 | 5000 只全历史约 2~4 小时 | 批量接口快，但有限频 |

**结论：行情 + 复权因子走 baostock（唯一能拿到因子的），估值/财务/行业走 akshare 或直接调东财。两边绝不在同一个字段上混用。**

### 3.2 复权的本质：不是「准不准」，是「用哪个基准」

设某股 7-15 收盘 10.00 元，每股派息 1 元，7-16 除息开盘 9.00 元：

| 口径 | 7-15 价 | 7-16 价 | 算出来的收益 | 问题 |
|---|---|---|---|---|
| 不复权 | 10.00 | 9.00 | **-10%** | 把分红当成暴跌，完全错 |
| 后复权 | 10.00 × f₁ | 9.00 × f₂（f₂/f₁ = 10/9） | **0%** | 正确，且历史值永不改变 |
| 前复权 | 10.00 × f₁/f_now | 9.00 × f₂/f_now | **0%** | 正确，但历史值会随每次新除权而改变 |

关键差别在**因子的分母**：

- **后复权** = 不复权价 × 累计后复权因子，因子只依赖「截至当日」已发生的除权事件 → **点-in-time 安全**，回测必须用这个；
- **前复权** = 后复权 ÷ 最新因子，分母用到「未来」的除权事件 → 同一段历史，明天再算数值就变了，且回测里等于提前知道了未来分红 → **只能用于看图**。

所以正确做法是根项目现在这套：

```
落盘：不复权 OHLCV + 除权事件表（dividOperateDate / backAdjustFactor）
回测：按需展开后复权
展示：再折算前复权
```

这样原始数据不丢、回测不引入未来函数、图表又符合看盘习惯。参考项目直接存前复权价，等于把「未来」固化进了历史，跑 5 年回测问题不明显，跑到 2008 年就会显著高估收益。

**一个必须记录的风险**：根项目 `data_validator` 的 R2.9 已发现 baostock 会**重算历史因子**（平安银行 2020-12-31 因子从 119.96 降到 99.79）。这意味着同一个回测今天跑和明年跑结果可能不同 → 必须把因子表**按快照版本存档**，回测结果绑定因子版本。

### 3.3 财务数据的时点问题（打分系统的隐形炸弹）

参考项目的财务数据只有 `REPORTDATE`（报告期末），没有公告日。用它做历史打分，等于在 2026-06-30 就知道 8 月底才披露的中报 → 前视偏差 1~3 个月，回测收益会明显虚高。

处理方式（三选一，建议第 1 种）：

1. 从东财补 `NOTICE_DATE`（公告日），按公告日对齐 —— 最准确；
2. 保守滞后：报告期 + 90 天（年报 +120 天）才允许使用 —— 简单可靠；
3. 财务维度只用于「当日推荐」，不进历史回测 —— 参考项目的做法，但会让打分无法回测。

## 4. 打分是核心：架构要围绕它重排

这是本轮最重要的认知变化。原方案把打分当成「四个功能之一」，实际上它应该是**一条因子生产线 + 一套评价体系**，回测则降级为「评价打分的工具」。

### 4.1 四层结构

```
因子层     Factor Registry：每个因子 = 纯函数 + 元数据（类别/方向/所需数据/来源/版本）
           7 大类：价值 成长 质量 动量 波动 流动性 情绪资金
   ↓
标准化层   去极值(MAD) → 缺失填充(行业中位数) → 行业中性(行业内 rank) → 市值中性(可选) → 标准化
   ↓
合成层     维度内合成 → 维度间加权(YAML 可配) → 综合分 → 横截面百分位 → 分档
   ↓
评价层     IC / RankIC / ICIR / 分层回测 / 多空收益 / 换手率 / 因子衰减 / 因子相关性
```

### 4.2 迭代闭环（决定这套系统能不能持续变好）

```
研报想法 → 写因子(20~50 行) → 单因子检验(IC+分层) → 相关性去重 → 进候选池
   → 合成打分 → 组合回测 → 上线每日打分 → 跟踪样本外表现 → 加权/淘汰
```

每一轮实验必须落一条记录：`experiment_id + 因子集 + 权重 + 数据快照 + 回测结果`。没有这个，三个月后你无法回答「上一版为什么更好」。

### 4.3 与参考项目的差距

| 参考项目 | 目标系统 |
|---|---|
| 6 维固定权重 | 因子注册表 + 7 大类 + YAML 权重 |
| 逐行循环打分 | 全市场向量化（秒级） |
| 绝对分 0~100 | 横截面百分位（选股可比） |
| 无因子评价 | IC/分层/衰减/相关性 |
| 分数不落库 | 每日快照 + 版本化 |
| 估值质量仅当日 | 补公告日后可历史回测 |

详见 `docs/scoring-engine-design.md`。

## 6. 依赖冲突提示（不采纳 vectorbt 的理由）

参考项目锁的是 `pandas==3.0.6`、`vectorbt==1.1.1`、`numba==0.68`；根项目锁的是 `pandas>=2.2.3,<3`（实测 2.3.3）。

两者不能共存。而参考项目用 vectorbt 的地方只有一个调用：`vbt.Portfolio.from_orders(size_type="targetpercent")` —— 这部分用 numpy/pandas 自己写约 80 行就能等价实现，还能精确控制 T+1 开盘成交、停牌顺延、涨跌停拒单等 A 股细节。

**结论：不引入 vectorbt/numba，自研组合回测引擎。** 少两个重依赖，少一层版本冲突，执行假设还更可控。
